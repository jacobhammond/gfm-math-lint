# ADR 0003: Lexical Zone State Machine vs. Full AST Parsing

## Status
Accepted

## Date
2026-09-30

## Context
Linters traditionally rely on an Abstract Syntax Tree (AST) generated by a full parser. However, standard CommonMark parsers:
1. Normalise, consume, or drop whitespace, backslashes, and comment nodes needed for in-place source code editing.
2. Require heavy C-extensions or external dependencies (e.g. `markdown-it-py`, `mistune`, `tree-sitter`).
3. Obscure the exact character positions and boundary conditions critical for fixing inline KaTeX equations.
4. Conversely, naive regex matching over raw document text produces high false-positive rates (e.g. matching a `$` inside a Python code block or inside a YAML header).

## Decision
Implement a hybrid **8-Zone Lexical State Machine** (`Tokenizer`):
- A line-oriented block state machine tracks structural zones (`FRONTMATTER`, `FENCED_CODE`, `DISPLAY_MATH`, `COMMENT`, `TABLE`, `PROSE`).
- An inline token scanner isolates inline zones (`INLINE_CODE`, `INLINE_MATH`) within permitted block zones.
- Rules only inspect their declared zones.

## Consequences
### Positive
- Retains exact source coordinates and raw whitespace for seamless diff generation.
- Zero false positives from code fences, frontmatter, or comments.
- Zero external C-extensions or third-party dependencies required.
- High-throughput scanning suitable for large documentation trees.

### Negative
- Complex nested Markdown edge cases (such as lists containing tables containing code blocks) require explicit state machine handling.
